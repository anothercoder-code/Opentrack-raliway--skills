# OpenTrack Rail 基础版 basic1

整理日期：2026-10-30。配套后端协议仍为 `0.33.1-zeroaccept1`。

这是当前已验证能力的基础发行版，沿用 `opentrack-rail` 名称、现有 CLI/MCP 和
配套后端。先完成用户当前工程，再按实际需要查阅进阶接口。下面的经验来自本次
原版 OpenTrack 操作、数据检查和工具回归；历史样例不代替另一份工程的实际验收。

## 安装与必要资源

安装包解压后只有一个 `opentrack-rail` Skill 目录；按 Codex 的 Skill 安装方式放入
对应的 skills 目录。后端随包位于 `backend/OTAI`。使用 Python **3.13.x**，依赖见
`backend/OTAI/requirements.txt`；独立目录布局见
[本地安装](local-installation.md)。原版英文铁路 OpenTrack **1.7**、合法持有的原生
模板和工程数据需要另行提供，不包含在安装包中。

数据根目录由 `OTAI_DATA_ROOT` 或所选 CLI 的 `--root` 明确指定。CLI 的 `--root`
命名参数与环境变量不是同一个参数。原版将读取的工程执行路径、文件名、站名及
文本使用英文可打印 ASCII；外部说明可以使用中文。

## 基础工作流

| 用户任务 | agent 要完成的工作 | 进入下一步的依据 |
|---|---|---|
| 新建工程 | 确认站数、股道、站外正线、停站需求和资源；准备真实路径及实测 SHA 的输入 | 输入落在所选生成入口的完整合同内 |
| 从零建站场 | 生成真实轨道、咽喉、道岔、站台图形、方向信号和跨文件连接 | 实际存档重读、图和引用检查通过 |
| 修改现有工程 | 在原路径准备、核对并应用受影响成员的补丁；先处理旧对象和目录缓存 | 写后重读证明目标字段已修改，其余内容按约定保留 |
| 原版保存与重载 | 检查当前绑定；在授权范围内执行原版保存、真正关闭并重新打开同一路径 | dirty 标记变化、磁盘写入及重新加载后的字段一致 |
| 联程仿真 | 运行当前工程并检查新输出中的出发、跨站、终到停车和共享资源 | 同一批输入、原版运行及输出能相互对应 |
| 闭塞与故障 | 使用同向跟随列车和指定故障，检查实际预约/释放、停车及恢复 | 结果来自原版输出；灯色另有实际界面观察 |

“生成完成”“已写入当前工程”“原版已加载”“原版已保存”“真正重载”和“原版已运行”
分别记录。agent 负责数据准备和解释；使用可靠的桌面工具直接操作，或在用户接受时
按 [用户引导模式](user-guided-operation.md) 给出短步骤。

## 选择基础方案

| 方案 | 范围 | 参考 |
|---|---|---|
| 简单多站联程 | 一站一文件，共享一套运行目录和一个 run；三站时为 10 个输入成员 | [单站文档生成](station-documents-project.md)、[三站从零流程](zero-start-three-station.md) |
| 三站八股道站场 | 三份站图；每站 8 条站台股道、4 座岛式站台图形、12 组 paired-End 道岔、16 架方向信号；站外 2 条正线；正常和故障两套运行数据，共 17 个输入成员 | [站场布局、生成和结果校验](station-document-layout.md) |
| 现有工程调整 | 保留原工程根目录、站图身份和运行绑定，修改所需依赖闭包 | [原位修改流程](station-document-layout.md) |

三站八股道方案固定为 `eight_platform_two_mains_5km`：每站四条 D 股道、四条 U
股道，站外是一条 D 正线和一条 U 正线。它不是四组独立的站间复线。车型使用
`CR400AF_8_PROXY_350` 继承代理参数，必须由输入显式接受其未标定范围。
岛式站台目前是图形对象，不代表已建立旅客容量模型。

`scripts/yard.py` 提供 `preview`、`stage`、`publish`；输入为六份 SHA 绑定的外部
原生资源和三站 recipe。agent 先按布局参考准备 UTF-8 request 文件，再调用实际
CLI。`stage` 的暂存回执不等于正式发布；`publish` 要求实际新目标、匹配的执行
根目录及 Windows x64 固定本地 NTFS，不覆盖既有目标。既有工程采用原位修改流程。

`scripts/yard_audit.py capture` 在运行前冻结输入及生成回执；实际运行后使用
`verify` 校验同一批新输出。校验器从真实存档重建共享资源，并采用 recipe 中的
实际站名；它本身不启动原版、不观察灯色。CLI 的实际选项可通过 `--help` 查询。

## 本次形成的操作经验

1. **在原工程上改。** 密度、信号、区间延长等连续调整应落在同一正式工程，
   维护一份候选和可校验前态，避免让用户反复导入不同版本。
2. **先澄清数量。** 分开确认站内股道、站外正线、方向、站台和联络关系；
   图面紧凑程度与 Edge 的物理米数分别设计。
3. **画出真正的站场。** 平行线和灰色矩形只是图形。咽喉要有真实连接的
   paired-End 道岔；跨文件连接需要互指，Routes/Paths/Itineraries 需要连续。
4. **限制输入到可靠范围。** 新图形位置使用 `alignment_x/alignment_y`；
   新信号对齐必须匹配其实际 owner End，拒绝信号 `0/0` 或方向不符。
   Station 的 `0/0` 与信号的规则分开处理，历史忠实克隆保留源值。
5. **信号图标和闭塞逻辑分别检查。** 在实际信号边界拆分 Route，检查同向
   列车共有的轨道、道岔和区间资源；外观、类型编号及静态配置不能单独证明防护。
6. **把持有旧对象的窗口处理好。** 关闭 Inspector 后真正卸载受影响文档；
   catalog 内容变更还要处理目录控制器缓存。旧进程退出可能写回旧数据，
   因此不能先替换目录，再让旧会话退出。
7. **保存要有磁盘证据。** 干净文档 Ctrl+S 可能不写盘；打开已打开的路径也
   不算重载。原版可能调整 Label 包围框等图形字段，须按已审查的允许差异比对，
   同时保护业务值和可变对象引用关系。
8. **按实际故障阶段诊断。** 输入对齐、Inspector 旧对象和启动菜单生命周期
   是不同问题。依据崩溃栈、具体动作和实际数据定位，不把所有崩溃归因于站场数据。
9. **验收具体行为。** stop 标志、Course 结束、零速终到和仿真 End 分开检查。
   正常排队也可能有警告；保留警告严重等级并解释分类，不把它们改称零告警。
10. **检查可调用工具。** 插件已启用不等于能截图或点击；运行时路径可能失效。
    窗口、焦点或弹窗变化后重新观察。空 `MainWindowTitle` 也不能证明没有窗口。
    尊重用户选择的操作者，不在用户拒绝代点击后继续重复布置界面步骤。

| 项目 | 本次证据 |
|---|---|
| 一站一文件、三站连接 | 当前 CEDAR/MAPLE/PINE 工程实际存档及跨文件引用检查通过 |
| 原版保存和真正重载 | 三份站图已完成；三个真实 Station Inspector 双击检查通过 |
| 正常联程 | 原版 GUI 到达 09:20 End；9 车各运行约 10 km 并终到停车；128 项共有区间检查通过 |
| 故障联程 | 原版脚本运行输出通过；指定故障使五列 D 方向列车受阻至 09:06，随后完成；128 项共有区间检查通过 |
| 原生告警 | 正常、故障两批各保留 45 条已分类 WARNING，均无 ERROR/FATAL |
| 新站名生成 | ALDER/BIRCH/CYPRESS 的独立 17 成员生成、Windows 发布和字节重读通过；这不是该新站名样例的原版 GUI 运行证据 |
| 可移植结果校验 | `capture/verify` 已交付，安装版 CLI 已重查真实历史故障输出；单元及独立边界检查记录保留 |
| 故障红灯停车 | 用户现场报告 CEDAR 故障信号红灯、GDD101 停在信号前；与 agent 截图观察分开记载 |

基础版不将尚未完成的黄/绿灯连续目视、终到后最终咽喉整体释放、可选 Inspector
guard 的原版运行验证、实车物理标定或原版全部 176 项功能列为已通过。可选 guard
保留静态组件，不自动启动，也不替换原版 EXE。

这里的原版验收针对已记录的特定工程和运行；另一份工程仍需绑定自己的输入、保存、
运行和输出证据。它不是适用于任意铁路设计的完整安全认证。

机器可读发行范围见 [基础版描述](basic-edition.json)。后续改进沿用本 Skill 和现有
工程身份，并在新的真实证据产生后更新相应验收项。
