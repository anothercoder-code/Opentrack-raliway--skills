# 既有车次、时刻表和接续的原生编辑

查明选定原生 `.run`、全部输入档案、运行的执行根和待改的确切车次后，调用
`opentrack_edit_current_operating_plan`。`source_project` 须包含实际工程文件清单及 SHA-256。
单图和多图工程可用同一接口。工程外的参考文件不属于此编辑；原版配置内的输出目录可保留既有结果。
每个 `operations` 动作按输入顺序执行。操作失败时，源项目不写入，候选不发布。
保存需 `preview_only=false` 以及独立的全新 `target_directory`。返还 `bundle-manifest.json`
给出原文件和候选哈希。进程启动和原版运行验收另行完成。

| 动作 | 用途 |
|---|---|
| `update_course` | 既有 Course11 车辆、交路顺序、速度类别、启停标记、闭塞模式、额外预约或释放时间等。 |
| `rename_courses` | 同时更新车次 ID 与能确认的时刻表键、间隔引用、接续、事件和选定运行图引用。两个车次 ID 交换也须放在同一动作内。车次显示号码可另用 `update_course` 修改。 |
| `delete_courses` | 删除车次及其行。存在外部引用时默认拒绝。确需解除依赖时给 `reference_policy="detach"`，以同时清除已识别的接续、事件和运行图引用，并重置间隔引用及偏移。受影响的选定事件从 `.run` 移除。 |
| `reset_course_itineraries` | 按选定图档与 DestInfo 的可用交路修剪过时选择。仍启用的车次至少须有一个可用交路。 |
| `update_timetable_row` | 改已有行的计划时刻和日偏移、停车或通过、计时点、最小停站、指定股道、延误分布及站间载重。按 `course_id` 和从零开始的 `index` 选择。设 `propagate_interval=true` 时按直接和多级引用同步计划到发。 |
| `insert_timetable_row`、`delete_timetable_row` | 依明确的既有行模板插入或移除位置并写回全车次索引。新行实际时刻清空，已保存的其他行保留。 |
| `generate_interval_courses` | 从既有车次复制计划，按 `number_step` 和 `number_position` 编号，按 `interval_s` 平移原版计划日和时刻。新复制的接续目标按同样规则编排，相关车次须同时建立或已存在。新增计划的实际结果字段清空。 |
| `update_connection` | 修改既有索引对应的最短或最长等待、接续目标、入口或出口等关联位置，以及按到达或发车判定。可用 `propagate_interval=true` 同步到直接间隔车次族的同位置接续。 |

一次操作可先更新两班相关列车，再发布同一份候选。例如编辑 1 号行的停车、股道和载重：

```json
{
  "action": "update_timetable_row",
  "course_id": "RDG09",
  "index": 1,
  "fields": {
    "stop_at_station": true,
    "dwell_s": 110,
    "track_id": "Down Main 2100",
    "delta_mass_t": 0.8
  }
}
```

同步区间时刻时，从任一成员选择相同站序中的一行并输入计划到发或日偏移。工具逐级
核对各车的站序、直接引用和秒数差，再按已存偏移写入同位置的所有成员。跨午夜会
重算日偏移。将计划时刻设为 `null` 时，该组相应时刻一并清空。车次引用、实际
时刻及接续字段保持。改站、改引用或调整区间偏移使用各自的编辑动作。

改站、插删或改交路时，检查时刻顺序与每个选定交路的站序。站点作为接续或间隔目标时，
移除唯一目标会被拒绝；同车次同站多次出现时，使用无法明确定位的结构改动也会被拒绝。
移动含接续的行须先处理该行接续。分合、等待、调度和股道能否按计划运行，以原版另行验收。
报告中的 `structural_readback_verified` 代表存档回读和引用检查，
`static_simulation_preflight` 是单独的运行准备检查。原版图表缓存与数据解释按已审计版本处理。

## 导入 OpenTrack TSV 或专有 XML

`opentrack_import_current_timetable_exchange` 接受 1.6/1.7 TSV 或 OpenTrack 专有 XML，
另存当前原生时刻表和必要的车次目录。将输入文件放入数据根的 `OTProjects` 或
`OTAI/workspaces`，并提交其路径和 SHA-256。使用 `source_project` 绑定该工程的 `.run`
与所有档案。用 `row_template.course_id` 和 `row_template.index` 提供同工程的原生行模板。

- `format` 使用 `opentrack_text` 或 `opentrack_xml`。
- `existing` 默认为 `reject`。明确指定 `replace` 时，替换输入车次的时刻行。
  指定 `merge` 时，按车次和行索引合并并保留未导入的行。
- 新车次须由 `new_course_templates` 明确映射到一个已有车次，以继承有效车辆和交路。
- 接续的拥有者、目标车次、站码和等待时间从原生输入读取并检查。
  连接到同一目标的记录合并时保留现有调度距离。
- 原版专有 XML 的连接地点和参考时间属性同时存在歧义时，必须声明要复原的处理顺序，
  并检查原版行为告警。设置 `import_xml_actual=true` 才接收 XML 的已保存实际时刻。

发布前核对档案回读和原版静态准备检查。区分本地原版运行产生的实际时刻和交换文件中的值。

## 从另一原生时刻表选择车次

`opentrack_import_native_timetable_archive` 直接读入 `.timetable` 的 `OTTimetable` v9 行。
用 `source_project` 绑定目标工程，用 `donor_timetable` 指定供体文件路径和 SHA-256。
`courses` 中每项填写 `source_course` 与已有的 `target_course`，一个目标对应一个供体。
同站码直接匹配。异名站码用 `station_mapping` 绑定。引用未选入的车次时，
在 `referenced_courses` 给出供体 ID 和目标工程的既有车次 ID。

- 每次导入一趟车的全部行，保留原生索引、计划时间、日偏移、停站、股道、载重和接续字段。
  目标已有计划时，选择 `existing="replace"` 明确替换这些车次的全部行。
  其他车次保留原有计划，车辆和交路继续使用目标工程的配置。
- 核对站序、时间顺序、接续目标、沿站间隔引用及延误分布。重复站点使目标无法唯一定位时拒绝导入。
  `import_actual_times=true` 才保留供体时刻表里已有的实际时刻。
- 发布包含替换路径和 SHA-256 的原生时刻表增量。将其放入独立的目标工程副本，保留该副本的运行绑定，
  再用[原版运行任务](native-simulation-jobs.md)核对实际发车、停站和终到。

## 成组导入原生车次和时刻表

`opentrack_import_native_service_archives` 把供体的原生 `.courses` 和 `.timetable` 一起导入，
在目标工程中增加有完整时刻表的车次。用 `source_project` 绑定目标工程，用 `donor_project`
绑定供体工程。两份库存都明确选定 `.run` 和关联档案的 SHA-256。用 `courses`
逐项给出供体 `source_course` 和尚未使用的 `target_course` 编号。

- 一起选入每条接续或站间间隔引用的两端。保存全部原生行、等待时间、联挂及分编标志、日偏移、
  股道和有序交路偏好，并按新编号回读接续双方。现有同站多次经过导致接续目标不唯一时，
  仍需用定向访问编排流程处理。
- 目标需要已有相同的站点、运行区段图档、沿途实际交路、限速类型索引、车辆和延误分布。
  可用 `train_mapping` 绑定定义相同的车辆别名，用 `itinerary_mapping` 绑定 Path、方向端
  和安全余量一致的交路别名。被遍历图档的原生内容须一致，以保留实际联锁和停车设施。
- 默认清零导入行的历史实际时刻；`import_actual_times=true` 时保留。发布两个原生档案和替换清单，
  将增量成对用于目标工程副本。静态预检不判断增开的车次之间是否有行车冲突。

跨午夜分编、接续、联挂的三车次样例已用正式入口保存并冷读，共九条时刻表行、六条接续记录。

## 导入 RailML 2.2 机车和编组

`opentrack_import_current_rolling_stock_railml` 将 RailML 2.2 的机车尺寸、质量、最高速度、
牵引力表、车辆顺序和拖车组另存为 `.depot` 与 `.trains`。明确选定同工程的
`engine_template`、`formation_template`，并设置 `accept_inherited_model=true`。
原版格式没有表达的车辆参数沿用模板，例如制动、阻力和部分功率设定。可用已有 `category`
覆盖编组类别。用 `on_conflict` 决定重名时拒绝、保留或替换已有记录。

牵引表按原版的单位名和整数转换规则读取。电力与柴油分别映射到对应通用供电类型。
逐台机车各占一个明确的位置；多节拖车可按原版组数量聚合质量和长度。
模板继承和轨道运行前准备检查分别记在报告中。实际牵引、制动和运营时分须随新车辆另行核验。

## 从原生车辆库导入机车、类别和编组

`opentrack_import_native_rolling_stock_archives` 从供体 `.trains` 和 `.depot` 读取原生记录。
用 `source_project` 绑定目标工程。各供体声明路径和 SHA-256。以 `formations` 指定供体名到目标名，
工具同步导入编组用到的机车和列车类别。可用 `engines` 或 `categories` 给依赖另取目标名，
也可只导入这些映射中单独点选的条目。仅导入机车只需供体 `.depot`，仅导入类别只需供体 `.trains`。

- Train16、Engine2 和 Category19 保留已有的编组位置、牵引曲线、效率表和车辆参数。
  新命名同步更新编组内的机车及类别引用。`OTEfficiency` 按原版保存的起始速度、损耗系数和功率损耗读写。
- 原版 Demo 与 Training 的旧车库使用 marker 16 的 `OTTrainList`、Train12、Trailer2 和 Category11。
  导入时根据 OpenTrack 1.7 解码器补齐当前档案字段。编组按原版顺序先排列机车数组，再排列拖车数组。
  已保存的机车及拖车标记、制动表和车辆参数保留。两库留下的未计算平均制动值按原位型保留，
  对应编组使用已保存的制动表。`legacy_class_upgrades` 记录迁移的选定车型和类别。
- 验证使用了本地原版 Demo 的 17 种机车、8 种编组、4 种类别，以及 Training 的 9 种机车、
  4 种编组、4 种类别。用户可以按需要选择单项或同时导入依赖。其他旧类版本需先检查对应的原版档案与编码器。
- 默认复用同名且图结构和字段一致的现有条目。参数不同的同名记录须使用独立名称。
  `existing="reject"` 要求目标无重名。
- 发布独立的 `.depot` 和 `.trains` 增量，现有车次继续使用自己原来的车辆。
  用 `update_course` 把所需车次明确改用新增编组，再从原版核对实绩。

OpenTrack 1.7 用导入的 Demo 和 Training Intercity 编组各跑完 12.000 km。两组长 368 m，
质量分别为 832 t 和 782 t，均在终点停稳。原始数据保留了 Demo Re 460 的两条效率记录和
Training Re 460 的空效率表。两车停稳且机械功率为零时，原版输入功率分别记录为 545 kW
和 0 kW。完整动力和能耗结果依赖所用线路、列车与仿真条件。

## 在既有线网编制多车运行计划

`opentrack_generate_existing_network_operating_plan` 以一份已有原生 `.run` 及全部关联档案为输入。
为每趟车指定原生车组、交路和速度类型，并按交路顺序列出全部站点的计划到发秒数和停车标记。
每个重复站点按它在交路中出现的次序填写，原生时刻表为每次出现保留不同的行索引。
交路可跨文档、进入分岔或汇入，也可由有限有序的径路组成闭合走行。

- 每班车独立选择已存在的原生 `Train`。接口按各编组长度、最高速度和边的方向限速检查时分。
- 声明停车的站点必须经有效的定向停车边到达，普通 End、站参考 End 和车站绑定一致。
  停车区可包含连续同站的多个轨段。位于停车区内部的道岔须与其配对方向端同属一个原生站场，
  已保存走行须完整给出该道岔的实际到达腿和出发腿。有效长沿选中的轨段计算。原版沿来车方向选第一个长度合格的专用标，
  后续通用车头、车中和车尾标可覆盖它。长度等于门限也合格。车头标和长度标以标牌位置为车头停点，
  车中、车尾标分别沿走行方向加半个和一个本次入站编组长。车头须在可核实的出站信号前或该点上，
  车尾须在该站的有向停车区内。
- 站参考端用于确定时刻表行。回执的 `stopping_point` 分别列出标牌位置、车头实际距离、
  车头所在 Edge 及沿边偏移、停车区入口至车头可用长度，以及停车目标速度 0 km/h。
  普通停车的指定股道在车头所在的有向 Edge 上核对。进出站时分下界按车头位置分段计算，
  跨到下一 Edge 时采用它的方向限速和车组最高速度，剩余段计入出站时分。通过站沿用站参考端。
  站参考端无信号且与出站信号分开时，在已保存走行中核对唯一出站信号和实际停车点。
  STATZ 候选的参考距为 1,880 米，出站停车点为 2,080 米，718 米编组计划跨站区内道岔停放。

- 道岔可以作为本地站台的边界。进入时从归属站场的道岔开始计算有效长度，两条外侧岔腿各按进路核对。
  反向可在道岔方向端的出站信号停车。Training 的两个入向车次和一个反向车次经原生保存、
  冷读和两向改长的独立检查。

- 终到尽头站台时，核对原有物理车挡和末段站区。存在独立 type 2 参考端时保留时刻表位置。
  无参考端的无信号车挡则用物理终点核对几何距离，已排班停车须有适合实际编组的原生停车标。
  已保存的停点距物理终点可以有余量。

- 分合编使用入站编组长度选标，同时核对实际车头后方容纳出站编组的空间，按当前单 Edge
  规则核对作业位置。后续停车使用变化后的编组长度。跨车次接续目前按已有参考端核对后车编排，
  动态接车起始坐标、原版制动曲线和实测轨迹随最终仿真验收。
- 对要交接同一车底的车次，明示 `turnrounds` 和 SHA-256 绑定的 `connection_template`。
  编组保持时，后续车次使用相同原生编组。同方向续驶用 `movement="continue"`，并从同一 End 发出。
  折返用 `movement="reverse"`，并从前车停车参考点的配对 End 发出。
  间隔须达到原生类别规定的最短折返时间。
- `mode="append"` 保留原计划。`mode="replace_plan"` 将候选中的计划替换为新增车次，
  要求选定工程没有关联事故集或原生运行图数据。新编号须与供体中的编号有区别。
- 首次排车且 `.courses`、`.timetable` 都为空时，使用 `mode="append"`，额外绑定
  `course_template_archive` 和 `timetable_template_archive` 的路径及 SHA-256。
  用 `course_template_id` 和 `timetable_template_key` 从相应现行原生档案中选记录形状。
  新班车的编组、走行、站序和到发取自目标工程和本次请求。车次控制、接续、间隔与
  历史实绩按原版初始化结构重新生成，供体记录全程只读。
- 保存时将所选原生依赖重定位到全新工程。原计划与既有运行输出不动。
  生成工具返回方向、停靠边长度、速度下界与原版静态准备结果。实际车次交会、能力和正点需原版实跑验收。

原版依据为 `0x63f6f0` 的同向停车标选择与车中/车尾偏移、`0x5d0a60` 的长度门限、
`0x64757c` 的车头位移和 `0x641814` 的零速停车目标。Reading 9 股道实档离线另存中，
209 m 编组选同一个 400 m 专用标，移动前后车头行程位置为 1925 m 和 1975 m，站参考端
保持 2025 m。相应进站下界为 86.625 s 和 88.875 s，出站段下界为 103.5 s 和 101.25 s。
独立新增车中标的实档使用相同长度的编组，1975 m 标牌给出 2079.5 m 车头位置，车头在
125 m 的原生站台边内前进 104.5 m 后停车。候选时刻表已另存并独立回读。
跨工作表实档的 90 m 编组在 West 图档取 350 m 处的车尾标，车头停点为 440 m。
同一个 300 m 站台连续跨两张图档，站参考端在 East 图档的 650 m 处。另存后回读了
1 股道和 120 s 计划停站。

### 同一车底的多段接续

在生成计划的 `turnrounds` 中逐段指定 `from_course`、`to_course` 和 `movement`。
折返用 `reverse`，要求上段终点和下段起点是同一站点的原生配对方向端。
同向继续用 `continue`，要求使用同一个方向端。连成一条车底周转时，各段选同一个原生 `Train`，
时刻须给该类别预留最短接续时间。接口将前车终到与后车始发写成原生时刻表的双向接续记录。

规划从前车当次编组的实际停车车头确定其当前进路。原版先从进路末端倒查各方向端，再正查上一条
进路。每个方向端先直接匹配后车交路的起点，再尝试其原生实际配对端，跨图档时通过已核对的连接器。
匹配站码、方向及后车交路首端后，回执 `native_linked_starts` 分别记录前车停车坐标和后车
`birth_end_key`。普通接续后车的起步位置在该交路第一条进路首端，局部偏移 0 m。
车中标或车尾标移动的是前车停车车头。后车第一个区间从自身首端计程。
当前入口要求关联各车选择一条普通交路。无法匹配和共用进路边界产生歧义时拒绝另存。
原版依据为 `0x620454`、`0x6204e4`、`0x64ca98` 和 `0x660680`。

Reading P9 冷读案例中，209 m 编组在 1975 m 的车中标前进 104.5 m，车头停于 2079.5 m。
同向候选以 RDG End 8 始发，折返候选以 RDG End 9 始发，两份均通过另存和静态预检。
带该车中标的组合接续仍待原版运行。

### 首选和备用站台

在车次的 `itinerary` 填首选交路，用 `alternative_itineraries` 按优先次序补充备用交路。
接口在原生 Course 中保存此顺序，并为每条交路核对同一个方向始发参考端、站点顺序、
时刻下界和各停靠边的有效长度。需要允许原版在不同股道间调配时，时刻表该站的 `track_id`
留空。已声明分编、联挂或车底交接的车次继续使用单条交路的明确停靠位置。

为各备选站台分别设置原生监视组后，可用
[原版站台选择验收](native-platform-choice.md)查明原版实际使用的终到站台及首选站台的占用情况。

### 同一站台的多次到访

在 `visits` 中按交路顺序逐行声明到访。即便两行使用同一站码和股道，停车、通过、到发时刻仍各自保存。
可用 `primary_reference_end: ["R2", 108]` 锁定该行首选交路中的图档和定向站点。工具回读
时刻表并列出从零起算的 `visit_index`、实际轨段和距始发点的沿线里程。备用交路仍按各自站序、停车区和
声明的 `track_id` 检验。

为未关联接续、只有一个交路的普通车次核验中途行，调用 `opentrack_verify_native_timetable_visits`。
提供 `output_directory`、`evidence_directory`、车次终到条件 `course` 和按索引递增的 `visits`。
例如以下两项可核验第 1 行停车、第 7 行通过。

```json
[
  {"visit_index": 1, "station_sign": "R2", "reference_end": ["R2", 108],
   "expected": "stop", "minimum_observed_dwell_s": 100},
  {"visit_index": 7, "station_sign": "R2", "reference_end": ["R2", 108],
   "expected": "pass"}
]
```

停车必须同时匹配原版实际到发与停车区内持续零速证据。通过必须匹配同站通过事件、对应里程跨越和
正速度。原版在停车发车时也可能写一条同站 `Pass`，其计划对比列可能把这条记录关联到下一圈。
接口用 `.st1` 和 `.vt` 定位真实通过，并在回执中保留原版计划时间列的差异。

同一 R2/108、股道边 R2/318 的两次到访分别位于 4,036 米和 154,036 米。原版两次对照均通过：
首停后通过时，第一次 09:05:45 到、09:14:00 发，第二次 09:47:17 通过。交换停车和通过后，第一次
09:05:13 通过，第二次于 09:47:50 到、10:00:00 发。两案均到达同一 R3 终点。

### 同股道分编和联挂

在同一个计划的 `composition_events` 中提供 `kind`、`main_course`、`other_course` 和
`station_sign`。同一主车可在原版运行窗口内依次执行多次分编或联挂，各事件按主车的实际交路站序排列。
分出车次可以从一次分编事件始发，随后在自己的终点参与一次联挂。每次事件在两趟车的时刻表
均有一个明确的定向停靠位置。
接口从主车的初始编组开始，逐次累计增减车辆，再用每站到发时的编组检查停靠边长和最短作业间隔。
每次事件生成一对各自绑定站点和对方车次的原生 Connection6。

- 主车的 `station_sign` 在交路中出现多次时，在事件中填写 `main_visit_index`，
  即主车 `visits` 从零开始的行号。首站是第 0 行，作业须选主车中途停车行。
  例如 `{"kind":"split","main_course":"MAIN","other_course":"DET","station_sign":"R3","main_visit_index":7}`
  选择主车第八条时刻表行。停靠方向、停车边、同站经过次数和实跑时刻分别核验。
- 分编子车从匹配的本车交路首端起步，起点行要标为停车。子车构成必须是能够从主车移除的确切部件，
  主车移除后须有机车。编制先主后子计划可预留共线出清时间。
- 两个有动力单元组成的主车可在一个明确的中途站将后部单元分出并反向驶离。填写
  `main_visit_index` 和 `reverse_split`，后者包括
  `parent_head_end`、`parent_head_signal_id`、`child_origin_end`、`child_origin_signal_id`、
  `detached_edge_id`、`retained_edge_id`。子车首行的 `primary_reference_end` 必须等于
  它车头反向指向的站内主信号端。工具用两车的真实编组长度复核母车停头、车尾和连接位置，
  以及进站进路对反向子车始发端的原生定位。此入口目前针对单一分编事件及每车唯一交路。
- 联挂主车先进入股道。另一车以该股道为终点，两车同时使用同向停靠边。平台须容纳组合后的列车。
  在后续停靠站，检查当时的累积编组。原生来车进路及其入口主信号均须容许占用股道接车。明确给出
  `occupied_entry_speed_kmh` 时，接口在候选中启用确切入口主信号的占用接车许可，
  并设置所选来车进路及其跨图续段的占用进入速度。
- 计划中的组合变化由原版仿真执行。分别记录存档推算的全长与实跑中的列车长度诊断值。
  从原版任务取命令输出、事件日志和实际到发记录。可将相同机车在每次分合前后相邻发车段的同速牵引力
  用作物理编组变化的独立证据。用
  `scripts/verify_native_composition.py --build <回执> --native-run <运行目录>` 复核。

同一主车的环线验收中，R2 联挂与 R3 分编分别于 09:26:18 和 09:47:15 发生，三趟车均终到。

### 分编后继续并重新联挂

在同一份计划中填写 `composition_events` 和 `turnrounds`。主车分编或联挂后可在终点用
`movement="continue"` 交给同向后继车次。后继使用同一方向端和同一列车类别，声明的原生 `Train`
须准确匹配剩余车辆的种类、标识和顺序。分出子车可沿自己的交路运行，随后作为供车与后继车联挂。
报告 `projected_formation_transfers` 记录存档推算。原版实跑用 `verify_native_composition.py` 核对
末站接续、后继停稳后重启和跨车次的同速牵引力。

环线对照中，418 米编组在 09:11:15 于 R2 分编，剩余 209 米编组于 09:32:27 在 R3
原方向端交给后继车次。29 个同速样本的接续前后牵引力比值均为 1.00。分出车沿自己的线路到达 R4，
原版为两车在 10:15:27 同时记录联挂。分编与重新联挂的牵引力比值分别为 0.50、2.00。

### 编组变化后换端

编组变化后的后继车次也可使用 `movement="reverse"`。前车同站到达端与后车发车端必须是原生配对端，
保留编组的两端均须有动力车辆。后继 `Train` 按新行进方向声明车辆，必须恰好是留下车辆的反序，车型、
车辆签名及列车类别须匹配。前车到达后仍按原生双向时刻表记录接续。核验脚本同时回读冻结车次的车型、
后继机车数组顺序、出发方向和实跑轨迹。具备 `.tsvP` 时，报告两段在相同低速下的实测牵引力。

Reading P9 试验中，两台 42 米教学机车在 10:36:02 实际联挂，随后在 Tilehurst 侧边界换端，11:02 从
WB/9 沿原停车轨段反向发车。两组用相同车辆和交路，后继声明的车辆顺序不同。前后机车交换后，在
0.7 和 1.4 km/h 的原版记录中均为 242.00 kN，保留原顺序的原版对照分别为 252.85 和 252.86 kN。
两组均实际折返。该差异验证教学试验中首机相关的牵引行为，锁定改用哪个驾驶室仍需驾驶端数据。
